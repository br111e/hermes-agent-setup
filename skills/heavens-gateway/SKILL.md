# Workflow
1. **Edit the local source of truth** (scratch `app.py`), or write a patch script in `/tmp` that does `raw.replace(anchor, new)` with `assert raw.count(anchor) == 1` (print the count on failure — it saves a loop).
2. `python3 patch.py` then `py_compile` the file; take the new `md5sum`.
3. **Deploy + verify in ONE SSH session** (write, md5sum, restart, md5sum again, health check — all in a single stdin script). Base64 the payload to survive shell quoting:
   ```
   # build /tmp/deploy.sh locally: "echo <B64> | base64 -d > /data/home/heavens/gateway/app.py && md5sum ... && cd /data/home/heavens && docker restart heavens-gateway && <optional: docker exec heavens-gateway data cleanup>"
   B64S=$(base64 -w0 /tmp/deploy.sh)
   printf 'bash -c "echo %s | base64 -d > /tmp/deploy.sh"; bash /tmp/deploy.sh; sleep 6; md5sum /data/home/heavens/gateway/app.py; curl -s -H "Host: api.heavens.ai.id" http://127.0.0.1:8080/health; echo; exit\n' "$B64S" | ssh -p 2222 ibssh_zze7yebb5rimzv3wipohbkj3yy@ssh.instabox.sh   # BoxB; sandbox instead: | bash /tmp/new_connect.sh ~/.ssh/sbx_cloud_ed25519 -o BatchMode=yes -o ConnectTimeout=25
   ```
   Both md5sums must equal the local file's md5.
4. **E2E test against the live API** with `urllib` (login as admin, exercise the new endpoints, check status codes incl. rejection paths like 409 full-key).
5. **Verify UI in the real browser** (`browser_exec`): login, drive the new UI, read the message element text. Screenshots: `cdp("Page.captureScreenshot", format="png")` then save base64; don't pass `None` to `cdp()` params (`DOM.getBoxModel` with non-int `backendNodeId` fails).
6. **Clean up test data** (`/root/.deepflow/*.json` in-container) and update the memory entry with the new deployed MD5.

# Pitfalls
- **pycryptodome GCM nonce**: `AES.new(key, MODE_GCM)` with no nonce uses a random **16-byte** nonce — but the WebCrypto client uses **12 bytes**. Always pass `nonce=secrets.token_bytes(12)` on the encrypt side or decrypt silently fails with 'could not be decrypted'.
- **pycryptodome RSA.construct(n, d)**: signature is `construct((n, e[, d, p, q, ...]))` — passing `(n, d)` puts the private exponent in the `e` slot; import still succeeds, RSA-OAEP decrypt then just fails. Store the full key as `export_key("DER")` base64 instead.
- **pycryptodome GCM decrypt**: `AES.new(key, AES.MODE_GCM, nonce=iv, tag=tag)` raises `TypeError: Unknown parameters for ECB` — the `tag` kwarg is not accepted at construction. Must do `c = AES.new(key, AES.MODE_GCM, nonce=iv); c.tag = tag; c.decrypt(ct)`. Encryption side (`encrypt_and_digest`) is fine.
- **24h stability ladder (31 Okt)**: on top of one-container-per-token, `wd.py` (v4) = 30s interval, threshold 2, browser UA probe, plus a DAILY `heavens-tunnel` restart at 21:00 UTC (04:00 WIB) so argotunnel connections never stay stale >24h. Watchdog container runs `restart=always`.
- **Two cloudflared containers sharing one tunnel token = load-balanced 502s.** CF edge distributes requests across all registered connectors; if a stale one points at a dead origin (e.g. old `--url http://caddy:80`), every request it gets returns a 16-byte `error code: 502` body — that string is cloudflared's error page, NOT Caddy's or Cloudflare's. Check `docker ps` for stray tunnels (they can carry random compose names like `interesting_keldysh`) and `docker logs <tunnel>` for `dial tcp ...:80 connect: connection refused`. Exactly one container per token. The symptom is not only 502s — two LIVE origins with different app versions produce a random 404/405/200 mix across repeated identical requests; the detector is a consistency loop (N× identical curl, compare bodies). `docker stop` is not enough: compose restart-policy `always` resurrects the stopped tunnel on the next daemon restart — also run `docker update --restart=no <container>` and confirm `docker inspect --format '{{.HostConfig.RestartPolicy.Name}}'` returns `no`.
- **`app.py` stores its HTML dashboards (ADMIN_HTML, MEMBER_HTML, REGISTER_HTML...) as single-line Python string literals**: newlines are the two-character sequence `\n` and single quotes are `\'` inside the file. A multi-line patch anchor written naturally will never match. Either (a) build anchors with an `esc()` helper that turns `'` → `\'` and real newlines → literal `\n` before matching, or (b) use `re.search` on the raw text. Regex backslash counting is the trap: the file has ONE backslash per escape, a raw regex string needs two — before writing any anchor, dump `repr()` of the raw slice around the target and match it byte-for-byte. Template literals in the JS (backticks, `${x...}`) are fine; it is the `\'` and `\n` that break naive anchors.
- **Sandbox auto-restore**: `/home/agent/heavens/` can be restored from snapshot — a file written in one session may revert before a later one. That is why the deploy MUST write, md5sum, restart, and md5sum-again in the same SSH session; never trust the file from a previous session.
- **UI JS convention**: `api()` returns `{ok, j}` — response body is `r.j`, not `r`. Any dashboard JS written against `r.field` silently no-ops (no exception, empty message).
- **Bare `/api/*` fetches in dashboards never reach the gateway**: pages are served under `/__api__/...` (prefix stripped) but absolute `fetch('/api/register')` resolves at the origin root and hits Caddy's `handle /api*` → panel → 404 `{"error":"not found"}` (that body shape is the panel's 404, not the gateway's). Make every fetch prefix-aware — inject `var __B__=location.pathname.indexOf('__api__')>=0?'__api__/':''` and fetch `__B__+'api/...'` — or add explicit Caddy `handle` rules for gateway paths.
- **Baked-in HTML drifts from endpoints**: before patching a dashboard form, dump the live string constant (e.g. `REGISTER_HTML`) and diff the fields the JS sends against the fields the endpoint parses. The live register form was still sending legacy `{username, password, invite_key}` while the backend expected `{email, password}` + email-verify flow — fixing the backend without aligning the form leaves the UI dead with no error in the logs.
- **Repeated in-place Python surgery on the same HTML file leaves duplicates + orphans**: two successive replace-based patches on `member.html` produced TWO full JS IIFE blocks, and a later surgical deletion left an orphaned ternary-continuation line → SyntaxError, page rendered with all dynamic fields stuck at `…` (no visible error anywhere). Rules: after ANY multi-step edit of a site HTML, extract the `<script>` body and run `node --check` locally before upload; when deleting a UI section, grep for the deleted element IDs across the whole file (HTML + every JS block + CSS) and delete every reference; if a file shows two `})();`, it has drifted and the surgical patch has to account for both.
- **Don't derive auto-labels from a growing list**: when adding N items in a loop while appending to `rks`, `len(rks)` already includes items added this loop — number labels from a captured starting offset.
- **Dropdown bind values must match backend expectations**: the UI sends the user-visible value (e.g. username); the backend must resolve it to the internal key (sk-...) explicitly — resolve both username and raw key in the API handler, otherwise binds silently do nothing.
- **Shared-key data model** (`keys.json`): `max_users` (int, 0 = unlimited) + `owners` (list of usernames). Claim/register flow must reject at capacity with 409; shrinking `max_users` below current `len(owners)` must be rejected; existing owners keep access.
- **Fuel bulk import** (`POST /admin/river-key/bulk`): split on whitespace/commas, skip tokens not matching the river token prefix and duplicates, report `{added, labels, skipped:[{token,reason}]}`; a UI success message should list every created label, not "N more" with an index that drifts.
- **CF 1033 with the tunnel UP = container-internal DNS failure, not a dead tunnel.** Symptom: `docker logs heavens-tunnel` repeats `lookup caddy on 127.0.0.11:53: no such host` → every proxied request fails at origin. Fix (persisten): pin the target service's IP in compose (`ipam: config: subnet` on the network + `ipv4_address` on the service) and point `--url` at that IP instead of the service name, so cloudflared never depends on Docker DNS. Applying an IPAM change: `docker compose up -d <service>` fails with "network ... has active endpoints" when other containers sit on the network — do `docker compose down && docker compose up -d` (data is in named volumes, safe). Compose SERVICE names (`cloudflared`, `caddy`) differ from container names (`heavens-tunnel`, `heavens-caddy`) — `docker compose up -d heavens-tunnel` says "no such service".
- **1033/530 dual-tunnel trap (30 Okt)**: `cloudflared2` (`heavens-tunnel2`) ran the SAME `CF_TUNNEL_TOKEN` as main with `--url http://172.18.0.7:8080` → 8 tunnel connectors total, CF argotunnel max 4/connector → overflow logged `"already connected to this server"`, main tunnel's connections went stale, CF edge returned 530 (1033 page) even though origin was healthy. Symptom: origin 200 locally, tunnel logs registered but requests 530 from edge. Fix: `docker stop heavens-tunnel2 && docker update --restart=no heavens-tunnel2`, deleted `cloudflared2` service from `docker-compose.yml` (in-place `cat >` to keep inode), `docker restart heavens-tunnel` → 5×200. Rule: ONE container per tunnel token.

Fix: edit IN-PLACE (`cat /tmp/Caddyfile > /data/home/heavens/Caddyfile` keeps the inode) then `caddy reload`; if a rename already happened, `docker restart heavens-caddy` rebinds the mount. Verify with `md5sum` host vs `docker exec heavens-caddy md5sum /etc/caddy/Caddyfile` — they must match.
